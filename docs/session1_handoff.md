**Architecture (decided — do not change)**
- Static PWA, TypeScript + Vite. No backend, no server calls, no API keys.
  Works offline after first load. Photos never leave the phone except by the
  user's own export.
- No ML in the decision path; deterministic maths. Same pixels in, same result out.
- The pipeline (`src/pipeline/`) is pure TS, no DOM/Node (enforced by
  `tsconfig.pure.json`); input is a plain RGBA buffer.
- Pixel contract: frames come from live `getUserMedia` (never the phone's
  camera app), saved as lossless PNG with no colour profile + JSON sidecar with
  SHA-256 of the file and of the pixels; Node reads them only via
  `scripts/lib/capture-files.ts`. sRGB per IEC 61966-2-1, D65 for XYZ/CIELAB,
  float64. Colour correction is **relative calibration against our own
  registered print**, not absolute colour measurement.
- Anything uncertain → RETAKE (card stage) or INCONCLUSIVE (classification).
  Never a guess. No demo mode, no mock results, show real errors.
- Never type reference data from memory when a source exists; derive from our
  data or ask. Report real-photo evidence separately from synthetic tests.
- In UI and docs the printed mat is the **"reference colour card"** ("mat" is
  fine in code).

## What Session 1 built

1. **Scaffold & deploy**: Vite 8 + TypeScript 7 PWA, hand-written service
   worker (offline, update prompt), Vitest, GitHub Actions → Pages (base path
   `/drugtest/`), local HTTPS dev (`npm run dev:https`).
2. **Reference colour card MAT v1** (`print/`, generated by
   `scripts/generate-mat.ts` from `src/pipeline/mat.ts`): A6, 4 corner markers
   (top-left has a white centre = orientation key), 9-cell ID strip
   (version + copy letter, odd parity), 30 patches of 10 mm (6-step grey ramp,
   5 extra whites on all sides, 16 reaction colours, R/G/B), 70 mm sample zone,
   50 mm scale bar. A4 sheet with copies A and B. Two copies are printed and
   **registered** (`profiles/mat_reference_1_A.json`, `_B.json`).
3. **Camera & capture**: rear camera, 1920×1080 requested (phones deliver
   1080×1920), live guidance in a Web Worker, data collection mode (tags,
   copy, phone model, IndexedDB, one .zip export matching `data/real/`),
   optional exposure/white-balance lock for registration shots.
4. **Card pipeline** (`src/pipeline/analyse.ts`): blur/exposure → card
   detection (pure TS: adaptive threshold, components, holed TL marker,
   clockwise search, verification by marker sizes, contrast, grey-ramp order
   and ID strip; mirror and two-card views refused) → ID strip → sharpness on
   the card → patch sampling (camera pixels only, trimmed median) → "Move
   closer" → glare → **flat-field** (plane fitted to the six whites, divided
   out) → residual uneven-light check → registered reference → **correction
   method B** (per-channel grey-ramp curves, then 3×3; method A = 3×3 only) with
   **leave-one-out CIEDE2000** as the reliability gate.
5. **Screens**: camera with live card outline + TOP arrow and plain-words
   guidance; result screen (verdict, straightened card, 30 patches
   before/after/reference, light figures, leave-one-out error, method).
   **No classification yet.**
6. **Scripts**: `register-mat.ts`, `validate-mat.ts` →
   `docs/validation/mat_v1.md` (full real-photo report).
7. **Tests**: 112 unit (incl. CIEDE2000 against all 34 rows of Sharma, Wu &
   Dalal 2005 to 4 dp), 3 real-browser pixel-contract tests, e2e tests on the
   built app with a fake camera (data collection export, result screen, offline
   on the live site incl. Pixel 7 emulation).

## Real-photo evidence (19 photos, 2 phones: Nothing Phone (3a), OnePlus Nord 5)

Full tables: `docs/validation/mat_v1.md`.
- Pixel contract holds on every photo (hashes match).
- Detection: correct card, copy and version on every photo with 4 visible
  corners, despite the uncut A4 sheet putting copy B in view, textured tables
  and paper sheen. Two early false detections that passed parity were found
  and fixed.
- **Accepted (PASS)**: Nothing Phone daylight and tube-light photos
  (leave-one-out 3.7–4.0 ΔE00), the 6 registration photos.
- **Refused**: OnePlus photos (correction unreliable, uneven light, glare),
  torch (glare on the glossy cap / correction), warm bulb (local cap shadow).
- Should-fail: blur, too far, covered corner, glare all refused; **the soft
  half-card shadow photo PASSES** (flat-field removes a smooth shadow; its
  correction error 4.2 is within the limit). Reported as the headline finding.
- Test colour (an orange-red **glossy** cap, used because no orange card was
  available): before correction it read up to 19.4 ΔE00 apart across lights and
  phones; after correction (method B) 20.1 across both phones, 13.2 within the
  Nothing Phone; among accepted photos 2.8 before vs 4.9 after. The cap is
  glossy and more saturated than any printed patch, so this says little about
  matte reaction colours — **Session 2 must measure consistency on its own test
  (haldi) photos.**
- Registration: the only registration shots were hand-held at dusk; the three
  shots per copy disagree by 5.2 (A) / 5.5 (B) ΔE00 after normalisation.
  Accepted under a **prototype limit of 6** (was 3).

## Decisions taken in Session 1 (all by the user, on real data)

- Flat-field the smooth light gradient, then RETAKE only on residual unevenness.
- Registration normalises each shot to its own white patches; schema v2.
- Optional exposure/WB lock for registration (untested on a real phone).
- Method **B** is the default (derived from the data, weak evidence).
- **Hackathon standard**: use the current photos; registration spread limit
  raised to 6; no retake before submission.
- Blur limit derived from data (680); sharpness measured on the detected card.
- Camera requests native modes (`resizeMode: 'none'`) after emulation showed
  Chrome cropping a portrait camera to a square.

## Known issues / what needs fixing (priority for the deadline first)

1. **Demo conditions matter**: accepted photos so far are Nothing Phone in
   daylight/tube light. For the demo: card flat on a plain table, no hand or
   phone shadow, fill the outline, Nothing Phone, daylight or tube light.
2. OnePlus corrections mostly fail the leave-one-out gate (6–8 ΔE00).
3. Soft half-card shadow is accepted (policy question, not a bug).
4. Registration precision is prototype-grade (limit 6); retake flat on a table
   in daylight with the lock later.
5. Covered-corner and glare photos are refused with less helpful messages
   ("Card ID unreadable", "Show all four corners").
6. ID strip margin is thin under torch light (17% vs 15%).
7. Not measured: detection speed on a cheap phone, Safari/iOS, cross-engine
   `Math.pow` determinism. Exposure/WB lock unproven on a real phone.

## Session 2 must build (mandatory for the submission)

1. **Kit profile format** (versioned JSON, like the card) and one fully tested
   profile: the **haldi test** — turmeric with a safe alkaline household
   solution (e.g. soap or baking soda water); yellow = NEGATIVE, red-brown =
   POSITIVE — a legal proxy for a real kit.
2. **Reading the sample zone**: find the test inside the zone and sample it
   (trimmed median, avoid highlights/rims/shadows), corrected with the card.
   Liquid in a glass is in the original plan; for the deadline a flat sample
   (stain on paper / strip) is enough, with liquid as a stretch goal.
3. **Classification** POSITIVE / NEGATIVE / INCONCLUSIVE in corrected CIELAB,
   with **INCONCLUSIVE bands derived from real haldi photos** (the spread of
   corrected colours per outcome), never from memory. Anything the card
   pipeline RETAKEs cannot be classified.
4. **Tamper-evident record**: timestamp, GPS (with accuracy), operator ID,
   SHA-256 of the capture PNG, card copy/version, kit profile id/version,
   verdict and analysis summary; **signed with a non-extractable WebCrypto
   ECDSA (P-256) key per device**, described plainly as "proves the record was
   not changed after signing on this device", not "proves who the officer is".
5. **Hash-chained log**: each record contains the previous record's hash, so a
   record cannot be removed from the middle, inserted or reordered later
   without breaking the chain. Say plainly that an offline phone cannot prove
   its own clock or GPS were honest.
6. **Searchable log screen** (date, operator, kit, result, place) with record
   detail, signature/chain verification in the app, and export.

**Data Session 2 needs from the user** (through the app, data collection
mode; new tags will be needed): haldi stains on paper, a few NEGATIVE (plain
dried haldi) and a few POSITIVE (haldi + alkaline solution, dried), on the
registered card, in daylight and tube light, ideally on the Nothing Phone —
enough to set the bands (e.g. 4–6 of each).

**Reasonable to skip for the deadline**: registration retake, the 15+ lighting
set, banding photos, liquid-in-glass reading, more kits, iOS testing,
performance tuning, deriving every provisional threshold, better messages for
covered corners/glare.
